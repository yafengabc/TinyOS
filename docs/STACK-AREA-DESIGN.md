# 栈区设计：每线程独立栈窗，无 guard（草案，2026-11-28）

状态：**提议，未实现**。本文是实现的基线；数字以 C3（rv32，4 KiB grain）为准。

## 1. 目标

- 线程栈不再从 `TOS_HEAP` 里 `malloc`：堆只装数据，大小可预测，回收确定；
- 每个栈有自己的窗口（4/8/16 KiB，按 `TOS_STACK`），由**默认拒绝**提供边界，
  删除每个窗口的 4 KiB guard；
- 线程栈由 PMP/MPU 保护：下溢立即 fault，而不是等下一次 syscall 的 canary；
- 大帧跨栈不再可能：栈下面任何未映射地址都 fault，`sub sp, 8K` 也一样。

## 2. 地址空间布局

```
 用户区顶部
 ┌───────────────┐
 │ stack N       │  4/8/16 KiB，2 的幂，按大小对齐，向下分配
 │ ...           │
 │ stack 0 (main)│
 ├───────────────┤
 │ 4 KiB gap     │  整个系统只保留这一个空洞
 ├───────────────┤
 │ data windows  │  span + heap（每个进程一个）
 └───────────────┘
```

- 栈区内相邻的栈在**别的线程的视图里未映射**，所以一个栈下溢进入邻栈也 fault；
- 放置有两种选择：
  - 栈区在数据区**上方**：最低的栈下溢会落进数据窗，边界必须留一个 4 KiB 空洞；
  - 栈区在数据区**下方**：栈向下生长进入的是更低地址的空闲区/其它栈（都未映射），
    **不需要任何边界空洞**。实现建议取后者，省掉最后 4 KiB；
- 栈窗大小仍是 2 的幂（`TOS_STACK` 的要求），对齐到自身大小，满足 NAPOT/MPU。

## 3. 保护视图

当前任务的 PMP/MPU 只映射：

```
code        [win_base, wx)
data        [wx, brk)            （heap 随 sbrk 往上长）
stack       当前线程的栈窗
(+ 平台的 trap 向量 / 设备项)
```

- 主线程的栈也在栈区，和 worker 一样，不再是“数据窗顶部”；
- 线程切换：只重写 **stack 这一条**（数据/代码不变）；
- 进程切换：整表重编程（和现在一样）；
- 删除 guard 区域和 ARM 的 landing 条：异常压栈失败就是 MSTKERR，直接杀；
  不再有“增长”，landing 没有存在意义。

## 4. 生命周期与回收

- `exec`：分配数据窗（`span + heap`）+ 栈窗（`TOS_STACK`，缺省 4 KiB）；
  argv/初始帧放在栈窗顶；任一步失败要把另一个窗口还回去；
- `thread_create`：内核从栈区分配栈窗，`thread_t` 记录 base/top；
- `thread_join` 成功、`thread_exit`：**立即**归还栈窗；没人 join 的线程
  保留栈和槽到进程退出（与 POSIX 僵尸一致，不是泄漏）；
- `exec` 失败、进程被杀、组长退出：整组的栈窗一并回收；
- **栈区用 buddy 分配器，不用 bump / 水位指针**：块大小就是 `TOS_STACK`
  的 2 的幂（4/8/16 KiB，QEMU 板 32 KiB），申请时按需二分、释放时与伙伴合并。
  这样每次 create/join 都会回到空闲链，不会出现 sbrk 那种“只升不降”；
  混合大小也不会像 first-fit 那样把 16 KiB 洞切成碎片；
- 计数器：`free` 和 `/proc/mem` 暴露栈区的 used / free / peak，测试用它判断
  “1000 次 create/join 后回到基线”；
- 耗尽：`thread_create` 返回 -1，不部分分配、不泄漏；
- 数据窗沿用现有 `win_alloc`；栈区和数据区在启动时切分（栈区大小可配置），
  数据窗不会吃进栈区。

## 5. 语义（明确写进 `lib.h`）

- **线程栈是线程私有的**。跨线程共享数据用 global/static；
- 把栈上对象的地址传给另一个线程并在那边访问，会 fault——不是未定义行为，
  是设计上的拒绝；
- `ps` 的 `wink` 显示**数据窗**大小；`stk/sz` 显示栈窗大小；不再有
  “栈 + guard 在同一个窗口里”的概念。

## 6. 平台差异

| 端口 | 行为 |
|---|---|
| rv32（C3、rp2350rv） | 默认拒绝；栈窗按页对齐（rp2350rv 要求页粒度） |
| rp2350 ARM | 默认拒绝；删除 landing，MSTKERR 直接杀并报告 |
| x86 / RP2040 | 无硬件边界：栈区布局照用，保留 `plat_user_stack_guard()`（canary + syscall 时的 `sp` 检查）。它只是检测：下一次 syscall 时发现 sp 在栈外或 canary 被踩，然后杀任务；**不能阻止**一次大帧（`sub sp, 16K`）直接跳过栈窗写进邻栈。构建期帧审计能拦住“单帧 ≥ 栈”，但拦不住“栈快满时再来一个中等帧”。所以这两个端口的栈隔离是**尽力而为**，不是保证；可以选配每栈 4 KiB 间隔来提高门槛，但那仍不是边界 |

> x86/RP2040 的软件守卫与栈区方案并不冲突：即使栈不在堆里，分工仍是
> “canary + sp 检查发现漂移，硬件不提供的事不做承诺”。

## 7. 收益（C3）

| 程序 | 现在（span+栈+guard） | 之后（数据窗 + 栈窗） |
|---|---|---|
| `sh` | 24 | **20**（16 + 4） |
| `tools` | 20 | **16**（12 + 4） |
| `help`/`top`/`ls`/`sleep` | 12 | **8**（4 + 4） |
| `edit` | 24 | **20**（16 + 4） |
| `csc` | 108 | **104**（88 + 16） |

- 每个带栈的实体省 4 KiB；
- 每个任务少一条 PMP/MPU 区域（不再有 guard 区）；
- 堆与栈不再共享窗口空间，`TOS_HEAP` 的语义变简单；
- 构建期帧审计从安全网降级为友好提示（越界必然 fault）。

## 8. 代价与风险

- 每个进程从 1 个窗口变成 2 个：分配器、失败回滚、`ps`、文档都要跟着改；
- 栈区碎片与地址空间上限（`MAX_THREADS=32 × 4 KiB = 128 KiB`）：buddy 分配
  只允许 2 的幂的块，混合 4/8/16 KiB 请求也不会产生 first-fit 那种不可用碎片；
  上限仍由配置决定；
- ARM 异常诊断变化（没有 landing 就没有故障帧）；
- x86/RP2040 需要两套策略，不能“删掉所有 guard”；
- 属于窗口模型的大改，需要 T3 实机；RP2040/Pico 2 当前未接。

## 9. 验收计划

1. C3 原型：主线程 + kthread 栈都进栈区、删 guard、只映射当前栈；
2. `kthreadtest`/`prodcons`/`deep`/`accept` 全过；
3. 窗口表（`ps`）对比本文第 7 节；
4. 故意下溢：立即 fault（不是下一次 syscall 的 canary），shell 继续；
5. 栈窗耗尽：`thread_create` 干净地失败，进程表/窗口不泄漏；
6. 回收：1000 次 create/join（含 4K 与 16K 混合）后栈区 used 回到基线，
   `free` 的栈区数字不漂移；不 join 的线程在进程退出后一并归还；
6. T1/T2；RP2040/Pico 2 的 T3 等硬件。

## 10. 明确不做

- 不提供跨线程栈指针（共享走 global/static）；
- 不为省一条 PMP 而做非 2 的幂栈大小；
- 不在 x86/RP2040 上假装有硬件边界。
