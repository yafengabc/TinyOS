# 嵌入式脚本引擎：先算内存，再决定放在哪

> 2026-11-03。起因：想在 TinyOS 里跑脚本，语法接近 Python/Lua/bash，担心解析器
> 把程序撑大、挤占 RAM。本文先量预算，再量引擎，最后给出部署位置。
> 所有体积数字都是本机 clang 23.1.4 / rv32imc / `-Oz` 与 `-O2` 实测，
> 方法见 §3，不是估算。

## 0 结论

1. **引擎本身可以做得很小**：宿主预编译 + 运行时 VM 是 **3.3 KiB（-Oz）/ 4.1 KiB（-O2）**；
   带完整语法的片上引擎 7.5 / 10.7 KiB；连编译器也放进固件 9.5 / 15.1 KiB。
   都远在“几十 K”之下。
2. **“解析器让程序变大”只对四成**：词法+语法占片上引擎的 40%，真正的大头是
   **在设备上做编译**带来的 64 KiB AST —— 它在 C3 的任务窗口里根本放不下。
3. **“塞进内核 = XIP = 不占 RAM”只在 RP2040 成立**。C3 的内核 `.text` 在 SRAM
   （`0x40380000`，ROM 搬进来的），每字节代码都由 RAM 出账——不过 2026-11-03
   把内核堆从 64 KiB 收回 32 KiB 之后，它有 **33 KiB** 余量，3.3 KiB 的引擎放得进去。
4. 因此推荐：**宿主编译 + 用户态 VM 程序**。窗口改成按需分配后，两块板给同一份
   8 KiB 映像的结果一样：32 KiB 窗口里 20 KiB 归映像+堆，引擎自己占 8 KiB，
   脚本堆约 12 KiB —— 想要更多，得让程序能声明"我要多少堆"（见 §2）。
   `TOS_SCRIPT_IN_KERNEL` 变体现在在 C3 上也立得住了（33 KiB − 3.3 KiB 引擎仍余
   29.7 KiB），RP2040 则本来就划算。

## 1 板上预算：先看能花多少

| | 内核 RAM 预算 | 已用 | **余量** | 任务窗口 | 栈 | 守卫 | 映像+堆上限 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| ESP32-C3 | 176 KiB | 144.5 KiB | **33 KiB** | 32 KiB | 8 KiB | 4 KiB | **20 KiB** |
| RP2040 | 128 KiB | 92.3 KiB | 36.6 KiB | 32 KiB | 8 KiB | 4 KiB | **20 KiB** |
| PC (x86) | 4 MiB | 很小 | 充足 | 64 KiB 起 | 32 KiB | 16 KiB | 视请求 |

窗口一列的数是**一个 8 KiB 映像的脚本程序**实际会拿到的窗口：窗口按需分配，
8 KiB 映像 + 8 KiB 默认栈 + 4 KiB 守卫 = 20 KiB，取整到 32 KiB（步长 16 KiB）。

两个必须说清的事实：

- **C3 的内核不是 XIP**。`board/esp32c3/kernel.ld` 把 `.text` 放在 `0x40380000`
  （SRAM 的指令别名），ROM 从 flash 把镜像搬进 SRAM 执行。所以“预编译进内核区，
  不占 RAM”这条在 C3 上不成立——内核每多 1 字节代码就少 1 字节 RAM。
  （余量曾经只有 252 字节；2026-11-03 把内核堆从 64 KiB 收回 32 KiB 后变成 33 KiB。）
- **RP2040 的内核才是 XIP**。`.text` 在 `0x10000000`（QSPI flash 映射），
  `.data/.bss` 在 `0x20000000`。那里“引擎进内核”确实是零 SRAM 代码代价，
  但用户窗口小得可怜：32 KiB 减去 8 KiB 默认栈和 4 KiB 守卫，映像+堆只有 20 KiB。

## 2 用户窗口怎么算

`kernel/process.c` 的 `exec` 用 ELF 的 **memsz** 算 span，所以 `.bss` 也算进映像；
窗口本身按需分配，向上取整到 `PLAT_APP_GRAIN`：

```
win = align_up(span + stack + PLAT_HEAP_GUARD, PLAT_APP_GRAIN)
```

`stack` 是 `PLAT_STACK_BYTES`（C3 / RP2040 上是 8 KiB），除非程序自己在源码里写了
`TOS_STACK(n)` —— 那会以 ELF note 的形式进映像，`exec` 在算窗口之前读它。所以这个
程序可以按自己的递归深度要栈，而不是跟着板子的默认值走。

C3（16 KiB 粒度）：引擎自身 span 约 8 KiB（5 KiB 代码 + 2.5 KiB 静态）→
`8 + 8 + 4 = 20` → **32 KiB 窗口**，其中 20 KiB 归映像和堆；引擎占掉 8 KiB，
留给脚本对象堆的约 **12 KiB**（8 KiB 默认栈时；如果树遍历真需要 16 KiB 栈，
这一项回到 4 KiB，所以递归深度是个要拿 `stk` 量的数）。

RP2040（16 KiB 粒度）：同样的 8 KiB 映像 → 也是 32 KiB 窗口、20 KiB 归映像和堆、
**约 12 KiB 脚本堆**。两块板的脚本预算现在一样了，因为限制它们的不是总内存，
而是"窗口 = 映像 + 栈 + 守卫"这个按需分配的规则。

栈这一项在 2026-11-03 晚从 16 KiB 降到 8 KiB 并改成可按程序声明（见
`docs/PLATFORM-DESIGN.md` §8.9.1），上面这 4 KiB 的差额就是那次改动直接换来的：
`ps` 的 `stk/sz` 列显示所有真实程序都在 1 KiB 以内，省下的 8 KiB 现在归引擎的堆。

同一晚还有第二项：**踩出栈底时内核会把栈翻倍、把堆的尾巴借给它**（§8.9.2）。对
引擎来说这一项是"顺手"，不是"保障"——生长检查的是 `brk`，而这个程序正是要把
12 KiB 堆吃满的那种，用掉 4 KiB 之后就没得借了。所以结论不变：引擎要么把递归
深度量出来（`stk`），要么继续 `TOS_STACK(16 * 1024)` 声明，别指望生长兜底。

这直接决定了引擎的 `.bss` 必须小：**对象堆要走 `sbrk`，不能做成静态数组**。
而"本程序要多少堆"的声明通道**已经存在**：`TOS_HEAP(n)`（`user/lib.h`，note
type=2，`docs/PLATFORM-DESIGN.md` §8.9.3）。引擎只要在源码里写
`TOS_HEAP(24 * 1024)`，`exec` 算窗口时就会把它算进去——8 KiB 映像 + 8 KiB 栈 +
24 KiB 堆 + 4 KiB 守卫 = 44 KiB → 48 KiB 窗口。要更大的栈就再加一行
`TOS_STACK(16 * 1024)`，两个 note 并存，窗口 48 → 64 KiB（192 KiB 用户区还装
3 个）。

## 3 体积实测：把引擎拆成七个部件

方法：每个部件一个编译单元，同一套 flag
（`--target=riscv32-unknown-elf -march=rv32imc -mabi=ilp32 -ffreestanding
-fno-builtin -fno-pic -fno-pie -fno-unwind-tables`），`-Oz` 与 `-O2`（内核默认档）
各编一次，用 `size -A` 取 `.text + .rodata`。部件之间只共享一个头文件，
所以数字可以直接相加，没有链接期去重。

语言子集（刻意做成“够用的复杂语言”）：
整数 / 字符串 / 数组 / 字典 / 函数与递归 / `if` `while` `for` / 字符串拼接 /
`print` `len` `str`；**没有**闭包、浮点、异常、REPL、模块系统。

| 部件 | 职责 | `-Oz` | `-O2` |
| --- | --- | --- | --- |
| `sys` | memcpy/memset/strlen/seq | 88 | 102 |
| `lex` | 词法（关键字表、数字、字符串转义、注释） | 1,118 | 1,774 |
| `parse` | 递归下降 + AST | 2,550 | 4,286 |
| `tree` | 树遍历求值器（不生成字节码的路线） | 1,994 | 2,196 |
| `comp` | AST → 字节码（跳转回填、函数表） | 2,506 | 4,978 |
| `vm` | 字节码 VM（栈机、调用帧、27 条指令） | 1,492 | 1,622 |
| `lib` | 对象分配、标记-清除 GC、字符串/数组、整数格式化 | 1,240 | 1,864 |
| `table` | 哈希字典（开放寻址，字符串键，倍增扩容） | 496 | 522 |

三种部署形态的合计（含字典）：

| 形态 | 组成 | `-Oz` | `-O2` | 运行时 `.bss` |
| --- | --- | --- | --- | --- |
| 树遍历（源码直接跑） | sys+lex+parse+tree+lib+table | **7.5 KiB** | **10.7 KiB** | 65.5 KiB（AST 64 KiB） |
| 片上编译 + VM | 上者把 tree 换成 comp+vm | **9.5 KiB** | **15.1 KiB** | 93.9 KiB（AST 64 + 编译表） |
| **宿主编译 + VM** | sys+vm+lib+table | **3.3 KiB** | **4.1 KiB** | **26.7 KiB**（其中对象堆 24 KiB） |

补充数据：

- 一份 9 行的 fib 脚本编成字节码是 **304 字节**（≈34 B/行），存进 littlefs 毫无压力。
- 两个引擎（树遍历 / 字节码）跑同一份脚本输出完全一致，说明这些字节是能工作的代码，
  不是被优化掉的无用代码。

## 4 四条结论

### 4.1 解析器不是主要成本

片上引擎 15.1 KiB 里，词法+语法 = 6.1 KiB（40%），字节码编译器 5.0 KiB，
VM 1.6 KiB，运行时库 1.9 KiB。也就是说真正“不可避免”的解析成本是 6 KiB 量级，
不是几十 K。撑大体积的是**功能**：浮点、闭包、标准库、错误信息 —— 不是语法。

### 4.2 AST 才是隐形大头，而且它在 C3 上直接出局

64 KiB 的 AST 池是“在设备上编译”的必要条件。C3 上一个刚起动的程序，窗口里
映像+堆只有 12 KiB，**一个 64 KiB 的 `.bss` 连 `exec` 都过不去**（需要的窗口
大于整个用户区，直接报 “needs N KiB, the whole user area is M KiB”）。所以：

- 想在 C3 用户态编译脚本，必须走**单遍编译**（边解析边出字节码，不留 AST）——
  可以把 64 KiB 和约 4 KiB 代码一起去掉，但语法检查、常量折叠这些就没地方做了；
- 否则就**在宿主上编译**（推荐），设备端只剩 VM。

### 4.3 放在哪，由“text 在哪执行”决定，不是由“谁是内核”决定

| | 引擎进内核 | 引擎进用户窗口 |
| --- | --- | --- |
| ESP32-C3 | 可行：余 33 KiB，3.3 KiB 代码由 SRAM 付账 | **可选**：5 KiB 映像 + 2.5 KiB 静态，脚本堆约 4 KiB |
| RP2040 | **划算**：text 在 XIP，只花 ~2.5 KiB 状态 | 同样 32 KiB 窗口、约 4 KiB 堆 |
| PC | 无所谓 | 无所谓 |

同一条代码在两种板子上最优解相反，所以构建系统里应该是一个开关，
而不是一次架构选择。

### 4.4 用户态引擎顺带买到了隔离

没有 MMU 的板子上，“VM 跑在用户态”仍然是实打实的好处：VM 有 bug 只死脚本进程，
内核还活着；脚本能碰到的只有 syscall 那一层。反过来，内核里的解释器一旦越界，
整个系统就没了——那 5 KiB 省下来的是 RAM，押上的是稳定性。

## 5 推荐架构

```
宿主                                   设备
────                                   ────
mkscript (Go)                          /bin/script（用户程序，约 5 KiB）
  source  ──►  .bc 字节码  ──写入──►     open → 读字节码 → 校验 → VM 执行
  （词法/语法/编译全在这里）              VM + lib + table（3.3 KiB）
                                        对象堆走 sbrk（约 4 KiB @ C3，声明后更多）
```

- **内核零改动**。脚本就是一个普通的用户程序，用现有 syscall。
- **编译器复用现有构建**：`cmd/tos` 已经是 Go 写的构建器，加一个
  `tos script build foo.sh -o /bin/foo.bc` 子命令，与 `mklfs` 同级。
- **字节码是数据不是代码**：存 littlefs，天然可写、可分发；不需要让 ELF 加载器认识它。
- **语法错误在构建时报**，带行号；设备端只处理“字节码不合法”这一种情况。

`os.*` 表把脚本接到现有 syscall 上（这张表也是权限边界）：

| 脚本 | 落到 |
| --- | --- |
| `os.print(...)` / `print` | `SYS_WRITE(1)` |
| `os.open/read/write/close` | 同名 syscall，fd 照常受进程表约束 |
| `os.gpio(pin, v)` / `os.adc(n)` | `SYS_GPIO` / `SYS_ADC`，或直接写 `/dev/gpioN` |
| `os.time()` | `SYS_TIME`（`plat_now_ns`） |
| `os.exec(path)` | `SYS_EXEC`，受窗口数量限制 |

字典建议直接用字符串键（`table.c` 的 522 B 就是这种），因为 shell 风格脚本里
“按键取值”比“按整数下标”常用得多。

## 6 分阶段实施（每步的体积预算）

| 阶段 | 内容 | 预算 | 前置 |
| --- | --- | --- | --- |
| P1 | 宿主编译器 + VM + `script` 程序，跑通 fib/循环/字符串 | 约 5 KiB | 无 |
| P2 | `os.*` 表 + shell 里 `sh foo.bc` | +0.5 KiB | P1 |
| P3 | 字典、字符串库（split/join/format）、数组方法 | +1.0 KiB | P1 |
| P4 | 片上编译（单遍），先给 PC/RP2040 | +6 KiB（无 AST） | P1 |
| P5 | 内核内 VM（RP2350 / 有余量的板子） | +2.5 KiB RAM | P1、内核腾空间 |

P1 的关键约束：`.bss` 必须 ≤ 2.5 KiB（值栈 + 帧 + 全局表），对象堆用 `sbrk`。
若按现在 spike 那样留 24 KiB 静态堆，C3 上要 48 KiB 窗口（24+16+4 上取整），
占掉 192 KiB 用户区的四分之一。

## 7 没量到 / 有风险的部分

- **程序外壳未计入**：打开文件、读字节码、把 `print` 接到 `write`、`os` 表本身，
  估计 +1~2 KiB。上面的 3.3/4.1 KiB 只是引擎。
- **软浮点未计入**：`double` 在 rv32imc 上要 vendored `__adddf3` 一族（compiler-rt），
  是另一个量级。bash 也没有浮点；建议先只做整数 + 定点。
- **错误信息/行号表**未做。真做的话，字节码里要留行号映射，脚本体积涨约 10%。
- **GC 只测了标记-清除的遍历**，没有块回收（spike 里分配器只前进）。真实实现
  要加空闲链表，估计 +300~500 B。
- **未在真机上验证** C3 窗口压力：4 KiB 堆 + 深度递归的脚本是否够用，得实测。

## 8 复现

测量用的 spike 在 `build/spike/`（构建产物目录，未入库），一文件一部件：

```
build/spike/{sc.h,sys.c,lex.c,parse.c,tree.c,comp.c,vm.c,lib.c,table.c,main.c}
clang -Oz main.c sys.c lex.c parse.c comp.c vm.c lib.c -o vm-spike.exe   # 字节码路线
clang -Oz -DTREE main.c sys.c lex.c parse.c tree.c lib.c -o tree-spike.exe
```

体积用同一套 flag 逐个编成 `.o` 后 `size -A`；见 §3 的命令。
