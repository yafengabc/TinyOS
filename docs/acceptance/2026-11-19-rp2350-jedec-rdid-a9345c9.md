What changed and how it was proved
----------------------------------
1. RDID is issued live.  `rp2350_flash_detect_jedec()` drives QMI direct mode
   by hand: flash_init_boot2_copyout() -> rom_connect -> rom_exit_xip ->
   DIRECT_CSR(EN|ASSERT_CS0N) -> 5 bytes exchanged through DIRECT_TX/RX
   (0x9f + four dummy bytes, five read back) -> DIRECT_CSR=0 ->
   flash_enable_xip_via_boot2().  The ROM's FLASH_OP entry cannot do this: it
   covers erase/program/read only.  The function is RAMFUNC because XIP is off
   while it runs, same as the existing write path.

2. The ROM value stays as the fallback.  rp2350_flash_detect() tries RDID
   first and falls back to the FLASH_DEVINFO data table when the part does not
   answer (0 / 0xffffff / an out-of-range capacity code).  On this board the
   RDID path wins, which is the point: FLASH_DEVINFO with
   BOOT_FLAGS0_FLASH_DEVINFO_ENABLE unset is the conservative 16 MiB default,
   an upper bound rather than a measurement.

3. Two traps, both worth keeping in the record:

   a. The capacity decode was written as `if (code < 0x20u || code > 0x24u)`
      followed by `1u << code`.  Those bounds are 32..36, so the shift is
      >= the type width - undefined behaviour.  clang folded it to poison at
      -O2 and then deleted the entire decode: the three volatile RX loads
      survived (all landing in the same register), the combine and the compare
      vanished, and the caller silently took the ROM fallback.  It looked like
      a compiler bug and was chased through tail-call and IPSCCP theories; the
      LLVM IR named it - `define internal fastcc void @rp2350_flash_detect_jedec`.
      The bounds are decimal 20..24 (0x14..0x18, 1<<20 = 1 MiB .. 1<<24 =
      16 MiB) exactly as on the ESP32-C3 port.  After the fix the IR keeps the
      combine and both images disassemble to three loads into three different
      registers, a compare against 0xffffff and `bl` (not a tail call) before
      returning.

   b. Why this is not a user-mode program: the result feeds
      plat_lfs_blocks()/ramdisk_init(), which runs at kmain() line 64 - before
      process_start_shell() exists, and the user ELF it would run from lives in
      the very filesystem it would be sizing.  On top of that the QMI registers
      are privileged (MPU on M33, PMP on RV32) and turning XIP off stops every
      flash fetch system-wide, so interrupts must be masked and the other core
      parked.  Those are kernel-only, boot-time properties.  flashinfo stays a
      user-mode reader of /proc/flash.

4. Expected effect on other parts: plat_lfs_blocks() already takes
   min(detected, configured), so a chip smaller than board.conf would now be
   clamped instead of mounting an oversized superblock; a chip at least as
   large as configured behaves exactly as before.  On this 8 MiB board both
   values agree, which is why df did not move - the change is that the number
   is now measured.
