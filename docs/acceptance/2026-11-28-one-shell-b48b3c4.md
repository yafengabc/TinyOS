## 为什么

`msh` 是默认 shell，结果是功能最全的 `sh`（脚本、`if/while`、`$(...)`、
`incr`）平时反而被测得最少；每加一个命令都要维护两套分派表，`help` 在 msh
下缺失、`incr` 只能待在 shell 里，都是这件事的后果。`sh` 在 `-Oz` 下是
16 KiB span / 28 KiB 窗口，和 `msh` 的 8 KiB span / 20 KiB 窗口只差 8 KiB，
不再值得为它保留第二套实现。

`help` 是另一件事：它是给 `tools` 这个**最常执行**的二进制背的死重，rv32 上
直接把它从 20 KiB span 推到 24 KiB（窗口 32 → 36 KiB）。拆成 `/bin/help`
后只有 `help` 自己付 4 KiB span / 16 KiB 窗口。

## 窗口（复核过公式）

运行时窗口是 `span + 4 KiB stack + 4 KiB grow + 4 KiB guard`；`grow` 是
`plat_window_grow_reserve()`，程序没声明 `TOS_STACK` 时内核多留一步给栈
增长。之前几张卡片写成了 `span + 8`（漏了 grow），本卡一并更正；证据是板上
`ps`：`sh` 的 span 是 16 KiB，`wink` 列是 **28**。

| 目标 | `sh` | `tools` | `help` | `msh`（冻结） |
|---|---|---|---|---|
| C3 / rv32 | 16 KiB span → **28 KiB** | 20 → **32** | 4 → **16** | 8 → 20（不再进镜像） |
| rp2040 / rp2350（ARM） | 24 → **36** | 24 → **36** | 4 → **16** | 8 → 20（不再进镜像） |

`help` 拆出去前（`371b63c`）rv32 `tools` 是 24 KiB span / 36 KiB 窗口；现在
20/32。ARM 的 `tools` 从 `-O2` 的 28/40 降到（`-Oz`）24/36，`help` 拆出后
仍是 24/36——ARM 的 Thumb 代码省不下那一个 span 阶梯。

## 实测（C3，默认镜像）

```text
tos> ls /bin | grep msh        -> （空；msh 不在镜像里）
tos> ls /bin | grep help       -> help 等；`ls -l` 显示 2300 bytes
tos> help | head -n 4          -> TinyOS help / Shell builtins (sh): ...
tos> ps                        -> ... 28  1.3/4  sh        (wink=28)
tos> sh etc/demo.sh            -> [script] if-ok、capture-ok、loop 0..2、
                                  after-loop i=3、break-at-2、done，全部通过
tos> accept.py -p COM4         -> 42/42 passed
```

第一次跑 accept 是 41/42：`reboot resets the chip` 找不到
`reboot: resetting the machine`，因为 sh 的 `reboot` 内建打印的是
`rebooting...`。删掉内建、统一走 `/bin/reboot` 后 42/42（`reboot &`、
`reboot > f` 也顺带变得和其它程序一致）。

## 没有做的

- **rp2040 / rp2350 的 T3**：板子没接，`accept.py` / `accept33.py` 的改动
  只做了语法和逻辑检查，实机结果记为 `NOT RUN`；
- **`msh` 的真实窗口没有复测**：它已不打包，20 KiB 是按同一公式从 8 KiB
  span 算出来的；要再量需要临时去掉 build.go 里的跳过；
- `msh` 的源码保留但不再维护；如果哪天要删文件，直接 `git rm -r user/msh`
  即可（没有任何构建路径引用它）。
