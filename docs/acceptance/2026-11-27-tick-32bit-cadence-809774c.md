## 根因

`g_ticks` 是 `uint64_t`，tick 里每秒 1000 次做四件事的节拍：

```c
if ((g_ticks % 50u) == 0u)   wdt_feed();      /* 看门狗 50 ms */
if ((g_ticks % 500u) == 0u)  ...              /* [U] cfg 启动跟踪 */
if ((g_ticks % 1000u) == 0u) led_toggle();    /* 1 Hz 心跳 */
if ((g_ticks % 10u) == 0u)   ...              /* BOOTSEL 串口逃生 */
```

`-O2` / `-Os` 把 64 位常量取模强度削减成乘法；`-Oz` 不做，生成
`__aeabi_uldivmod`（RV32 是 `__umoddi3`）调用。每次约 3k 周期，一个 tick 四次，
150 MHz 下约 12.5k 周期 = 83 µs，占满核 8.3%。只有 core0 会走到这一段
（`id != 0` 在 `[U] cfg` 之前就返回），所以现象是“只有 core0 慢”，和调度器、
扫描、tick 频率都无关。

clang 产物对照（ATK M33 SMP，`plat_timer_tick` 符号）：

| 配置 | 函数大小 | div/mod 调用 |
|---|---|---|
| `-O2` | 1,058 B | 无 |
| `-Os` | 1,050 B | 无 |
| `-Oz`（修复前） | 676 B | `__aeabi_uldivmod` |
| `-Oz`（修复后） | 652 B | 无 |

这也解释了为什么 `-Os` 的 smpbench 一直是 2.02：它本来就不吃这个亏；被影响的
只有 `-Oz`。

## 修法

```c
tick32 = (uint32_t)g_ticks;      /* tick 里只加这一次 */
if ((tick32 % 50u) == 0u) ...
```

32 位常量取模在两个档位下都是乘法。四个周期最大 1000 tick，截断只在 49.7 天
回绕时改变相位（不是速率），而且 `plat_timer_init()` 每次启动都会 `g_ticks = 0`。
RV32 板同样处理（`__umoddi3` 的同一风险）。

## 板侧数字（ATK M33 SMP，DWT CYCCNT，由板侧执行）

| 指标 | `-Oz` 修复前 | `-Oz` 修复后 |
|---|---|---|
| core0 tick 体 | 12,508 周期（83 µs） | **219 周期（1.5 µs）** |
| core0 worker（12M 迭代） | 400 ms | **353 ms** |
| smpbench speedup | 1.87 | **2.01** |

core0 worker 回到和 core1 相同的 353 ms：core0 独有的每 tick 开销已经不在，
剩下的 tick 成本两核相同。

## 对 `-Oz` 结论的影响

`docs/acceptance/2026-11-27-user-opt-knob-a626381.md` 里 `-Oz` 的 1.85–1.90x
是带着这个 bug 测的，不能作为“`-Oz` 扩展性差”的证据。`-Os` 的 2.00–2.05x
不受影响（它不生成除法调用），所以“八个 RP2350 硬件目标用 `-Os`”的决定不变；
如果要重新评估 `-Oz`，用本修复后的镜像按 `docs/TESTING.md` 5.4 重跑 smpbench。
