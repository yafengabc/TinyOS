## 根因

`g_ticks` 是 `uint64_t`，tick 里每秒 1000 次做四件事的节拍：

```c
if ((g_ticks % 50u) == 0u)   wdt_feed();      /* 看门狗 50 ms */
if ((g_ticks % 500u) == 0u)  ...              /* [U] cfg 启动跟踪 */
if ((g_ticks % 1000u) == 0u) led_toggle();    /* 1 Hz 心跳 */
if ((g_ticks % 10u) == 0u)   ...              /* BOOTSEL 串口逃生 */
```

`-O2` / `-Os` 把 64 位常量取模强度削减成乘法；`-Oz` 不做，生成
`__aeabi_uldivmod`（RV32 是 `__umoddi3`）调用。每次约 3k 周期，一个 tick 四次，
150 MHz 下约 12.5k 周期 = 83 µs，占满核 8.3%。只有 core0 会走到这一段
（`id != 0` 在 `[U] cfg` 之前就返回），所以现象是“只有 core0 慢”，和调度器、
扫描、tick 频率都无关。

clang 产物对照（ATK M33 SMP，`plat_timer_tick` 符号）：

| 配置 | 函数大小 | div/mod 调用 |
|---|---|---|
| `-O2` | 1,058 B | 无 |
| `-Os` | 1,050 B | 无 |
| `-Oz`（修复前） | 676 B | `__aeabi_uldivmod` |
| `-Oz`（修复后） | 652 B | 无 |

这也解释了为什么 `-Os` 的 smpbench 一直是 2.02：它本来就不吃这个亏；被影响的
只有 `-Oz`。

## 修法

```c
tick32 = (uint32_t)g_ticks;      /* tick 里只加这一次 */
if ((tick32 % 50u) == 0u) ...
```

32 位常量取模在两个档位下都是乘法。四个周期最大 1000 tick，截断只在 49.7 天
回绕时改变相位（不是速率），而且 `plat_timer_init()` 每次启动都会 `g_ticks = 0`。
RV32 板同样处理（`__umoddi3` 的同一风险）。

## 附：影子变量换成逐点内联（`b26e93a`，2026-11-27 复测）

上面记录的是“函数顶部 `uint32_t tick32` 影子”的写法。本机在 ATK 上复测，
根因数字与上面的 12,508 → 219 周期、core0 400 → 353 ms、smpbench 1.87 → 2.01
完全一致；但影子变量要在 tick 的几次调用（`wdt_feed`、`led_toggle`、启动跟踪、
BOOTSEL 轮询）之间保持活跃，`-O2` 下多付约 1.2%：

| 版本 | CoreMark（`coremark 5000` ×3） | 总 ticks |
|---|---|---|
| 影子变量（`809774c`） | 472 / 472 / 472 | 10,573–10,581 |
| 逐点 `(uint32_t)g_ticks % N`（`b26e93a`） | 478 / 480 / 480 | 10,402–10,446 |

改动前（`8832043` 之前的 `-O2` 构建）是 478（10,450–10,457），说明 472 是影子写法
带来的，不是板子漂移。`-Oz` 两写法相同（CoreMark 480、smpbench 1.96–1.97），RV32
也相同（`smpbench 1250000` 1.92–2.00）。逐点写法只大 36 B（143,868 vs 143,832）。

测量条件：`TOS_OPT=-O2|-Oz` + `TOS_USER_OPT=-O2`（板上默认已是 `-Os`，这里显式覆盖），
ATK-DNRP2350AM，UART0 COM14；每组取 3 个有效样本，丢输出的轮次重跑
（`build/bench_retry.sh`）。

## 附二：复核与测试（本机，`dc2615a`，2026-11-27）

**测试**：T0 `go test -count=1 ./...` + `go vet ./...` PASS；T1 18/18 PASS；
T2 smoke `rv32` / `rv32smp` / `arm` 均 `SMOKE TEST OK`。这是 `b26e93a` 之后的
代码，和上面 `809774c` 那条不是同一棵源码树。

**静态核对**（ATK M33 SMP，`plat_timer_tick` 符号，`TOS_KEEP_SYMS=1`）：

| 版本 | `-O2` 大小 | 调用点 | `-Oz` 大小 | div/mod |
|---|---|---|---|---|
| 影子（`809774c`） | 894 B | 13 | 652 B | 无 |
| 逐点（`b26e93a`） | 928 B | 13 | 660 B | 无 |

**关于 1.2%**：两种写法的调用面完全相同，影子版还小 34 B；影子本身只是把一次
`g_ticks` 读取换成一次 32 位寄存器保存。按 10,450 tick 折算，1.2% 相当于每个 tick
约 16 µs（约 2,400 周期），这不可能来自这个 live range，所以 472 与 478 的差
**不能直接归因于影子写法**。两个镜像的 `.text` 相差 34 B，而 RP2350 上 1% 量级的
布局敏感此前已经出现过（`-Oz` 时期窗基址/代码位置变化）；影子版的三次 472 是
同一个镜像的重复，未覆盖“同镜像重刷”这一层。

要归因的话，做一个对照就够：在逐点版本里补 34 B 的 `__attribute__((used))` 填充，
让两版 `.text` 长度和后续函数地址一致，再各测 3 次；差值消失即为布局，保留则
影子写法确实有代价。代码本身取逐点写法没有问题（少一个跨调用 live range，且
`-Oz` 下两版一致），只是注释和本卡不应把 1.2% 写成已证实的因果。
