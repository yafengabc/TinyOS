## CSC 链路（板端，rpi-pico-smp）

链：`csc <c> <rir>` → `rvm <rir>` → `rcc <rir> /bin/<name>` → `<name>`；
三条路径的输出都要等于 `tests/onboard/*.expected`。

| 用例 | 结果 | 证据 |
|---|---|---|
| `cover` | **5/5 PASS** | rvm 与 native 均等于 `cover.expected`，且两者一致 |
| `state` | **5/5 PASS** | rvm 与 native 均等于 `state.expected`（turns/sum/readsum） |
| `ready` | **5/5 PASS（修复后）** | rvm 与 native 均等于 `ready.expected`，且两者一致 |

修复前（a97f74c 镜像，COM30）：

```text
csc /tests/ready.c /tests/ready.rir     # ok
rvm /tests/ready.rir                    # ready=1 / y=0，与 ready.expected 一致
rcc /tests/ready.rir /bin/ready         # rcc: thumb1: add needs a low register
                                        # /bin/ready 未生成，native 无法执行
```

根因：`e_add_imm`/`e_sub_imm` 在 `rn == SP` 且立即数不是 4 的倍数（或 >1020）时
落到通用路径，而 Thumb-1 的双寄存器 `add/sub` 不能拿 SP 当源；`ready.c` 触发的是
`add rd=3 rn=SP imm=6`（结构体字段偏移）。修法：该分支先把 SP 物化到低寄存器
（`movs rd, sp`），再用 `adds/subs rd, #imm` 补足，原 4 倍数快路径不变。
改动仅在 [thumb1.inc](file:///d:/projects/TinyOS/user/rcc/thumb1.inc) 的两个函数。

验证路径：host gcc 构建 thumb1 rcc 先复现与原镜像一致的报错；修复后 `cover/state/ready`
三个 RIR 均能生成；把重新构建的 rcc 经 `goc32 -pack` 打成 LZ4TOS 信封，
按 `rx` 协议上传到 `/bin/rcc`，板上重跑三条链 **15/15**，原 accept 回归 **14/14**。

## 未覆盖

- 灯带目视：Pico 未接 WS2812，`NOT RUN`；GP25 blink 已目视确认。
- `scripts/rp2350/reboot_soak.py` 原脚本面向 UART 常驻句柄，CDC 重启会重新枚举、句柄失效，
  直接跑会在第一轮抛 `ClearCommError`；上表的 `20/20` 来自临时 CDC 重连写法
  （判据保留：重连后必须有提示符，且 shell 自报 uptime ≤5 s；实测 ≤0.24 s）。

  重跑整轮 20/20，判定为主机枚举抖动，不是固件复位变慢。

## notes

- **验收脚本自身有 4 处 bug（本次运行前已修，未提交）**：
  1. `rp2040/accept.py`：`read_until_prompt()` 先 `rstrip()` 再匹配 `"tos> "`（含尾空格），
     条件永不成立，每条命令等满 15 s；改回直接 `endswith(PROMPT)`；
  2. `rp2040/accept.py`：`free` 检查找 `free: N`，实际输出是
     `kernel heap  total used free peak` 表格，改成取该行第 3 列；
  3. `rp2350/pio_accept.py`：`--no-flash` 附着到空闲 shell 时不发换行，提示符不会重印，
     报 “no prompt in 25s”；附着前补一个 `\r\n`；
  4. `rp2350/pio_accept.py`：检查 0 通过时仍打印 “no prompt in 25s” 备注；改为仅失败时给备注。
  四处都只修正判定/等待方式，不放宽任何判据。
- 第一次带 `--uf2` 的运行在刷机后 `boot`/`identity` 已 PASS，随后因中途再次拔插 USB
  触发 `ClearCommError` 中断，属主机侧句柄失效，不是固件失败；重启后按“已运行”模式
  重跑得到上表结果。
- RP2040 无 MPU/PMP，`prot` 四项本就不在可执行项内；未按“适用子集”改写成 24/24。
- **`user/rcc/thumb1.inc` 修复（本地，未提交）**：`e_add_imm`/`e_sub_imm` 的
  `rn == SP` 非对齐分支改为 `movs rd, sp` + `adds/subs rd, #imm`；对齐快路径不变。
- **上传过程与工具修复**：`tosput-cli`（现更名为 `tosput`）原节拍 256 B/1 ms 在 RP2040 CDC 上偶发丢 1 字节，
  报 `NAK r5(len … dec …)`，42 KB 的 ELF 在 41% 中断，`/bin/rcc` 一度被截断到 19 KB；
  当时用 64 B/5 ms 的临时发送器完成恢复。随后扫描节拍：256 B/1 ms 仍不可靠
  （3 次 42 KiB 有 2 次停在 chunk 24–27），256 B/2 ms 连续 10 次零 NAK
  （42 KiB 22.7–25.4 KiB/s，128 KiB 26.2 KiB/s），最终 `writePaced` 定为 256 B/2 ms。
  约 26 KiB/s 已是当前协议与 littlefs 的上限（每块一次 ACK + 落盘），再提高主机节拍只会丢字节。
- **`/bin` 只认 LZ4TOS 信封**：`build/fs-stage/bin/rcc` 是打包前 ELF（42 160 B），
  直接上传会被 `exec` 拒绝；经 `goc32 -pack` 打成 25 656 B 信封后上传
  （`hint 81920/16384/0`），板上可正常加载。
