## 为什么补这一轮

Thumb 的三条验收（#38 RP2040 / #40 Pico 2 ARM）都只在 ARM 侧跑过。板子有另一侧，
验收口径也要求 RP2350 两端都过，所以把同一套语料用 RV32 后端重新生成一遍：

```sh
python scripts/rp2040/thumb1-prep.py --script ../tinyos-script --arch rv32
```

`--arch rv32` 走的是 `rcc.c` 里已有的 `RCC_ARCH_RV32` 后端，期望输出仍由宿主 `rvm`
产生、仍写进 `build/thumb1/expected/`，所以运行器（`thumb1-run.py`）和金标文件一行没改
——同一批 44 个程序、同一份判据，换的只是后端。

## 两个副产物

1. **`file1` 的 `write()` 返回值**：RV32 与 M33 一样返回 5（正确），RP2040 与宿主
   `rvm` 返回 24。这给 #43 多了一个数据点：可疑的是 RP2040 native 与解释器，不是
   Thumb-2/RISC-V 代码生成。
2. **1 MiB littlefs 在 RV32 端正常**：同一个 87 文件/1 MiB 的暂存集在 RV32 SMP 上
   直接启动并跑完，而单核 ARM 目标同条件起不来（#42）。#42 的怀疑范围因此收窄到
   "单核 ARM" 这一侧，与 littlefs 大小无关。

## 结论

RV32（Hazard3 双核）**上板通过**：心跳 6/6、37 项严格比对两轮全过、7 个观察项无
fault。至此同一套 44 个程序在三个后端上都验过：Thumb-1 / RP2040（#38）、
Thumb-2 / M33（#40）、RV32 / Hazard3（本卡）。
