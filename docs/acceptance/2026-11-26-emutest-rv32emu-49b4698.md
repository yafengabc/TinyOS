## 为什么

`tostest emu|emutest|bench` 还在找 `build/rv32emu-c.exe`，传 `-clk wall`，
期望清单也按几周前的镜像和 C 模拟器写。`emutest` 只在启动失败或 reboot 失败时
返回非零，**WARN 从来不影响退出码**，所以清单烂掉很久没人发现。

## 仿真器入口

```text
findEmu()         build/rv32emu(.exe)（$TOS_EMU 仍可覆盖）
emu build         cd rv32emu && go build -trimpath -o build/rv32emu(.exe) .
startEmulator()   -elf <kernel> -ramdisk <ramdisk>，去掉 -clk
```

Go 模拟器按 APB 周期计时（1 指令 = 1 周期 @80 MHz），宿主机实际速度约为名义的
四分之一，所以客户机 `sleep 500` ≈ 2 s 墙钟、`hold 3` ≈ 12 s。旧脚本的 4 s
上限会把命令截断，后面的检查全在看上一条命令的输出；现在单条上限 40 s，
整轮约 45 s。

## 期望刷新（按 2026-11-26 的 C3 镜像）

| 检查 | 旧 | 现在 |
|---|---|---|
| `ps` shell 窗口 | 32 KiB | **16 KiB**（C3；32 是 rv32 QEMU） |
| `stk 4` | 32 / 8.x | **24 / 8.3/16** |
| `sleep 99999999` | "longer than 3600000 ms" | `max 3600000` |
| `cd /dev` | `/dev tos>` | 提示符不再带 cwd |
| `ls /dev` | gpio0 / gpio21 | rgb0 / gpio / adc |
| `deep` | 6 层存活、长到 16 KiB | `deep 3` 长到 8 KiB 存活；`deep 6 0 8` 必死 |
| `script` | `source etc/demo.sh`（msh） | **`sh etc/demo.sh`** |
| `py demo.py`/`pytest.py` | 有 | 删（`py` 在 defaultUserExclude） |
| `hold` | 10 个后窗口耗尽 | 7 个后**进程表满**（max_procs=8） |
| reboot | 最后，表满 | 表满之前；只认 reset 之后的提示符 |

两条都是**测试自身的错**，不是镜像回归：

- `source etc/demo.sh` 在 msh 里跑。msh 开头就写明不支持 if/while/`$(...)`，
  所以每行都被当程序执行（`exec: '/bin/if' not found`）。脚本语言在 `/bin/sh`。
- `reboot` 放在 10 个 `hold` 之后：`reboot` 本身是 /bin 程序，进程表满时连
  创建都失败——旧的 "reboot observed=false" 是这个原因，不是模拟器不支持。
  另外旧代码用整段会话文本找第二个提示符，第一次启动的 `tos> ` 一直留在缓冲区，
  这一条也可能假通过；现在只看命令之后的文本。

## 内核缺陷（2050c2a）

进程表满、线程槽还有空时，`proc_create_claim()` 打印
`exec: process or thread table full` 后调用 `proc_retire(p)`；那条线程
`p->proc == NULL`，而 `proc_retire()` 无条件关 `MAX_FDS` 个描述符 →
`proc_fd_table()` 返回 NULL → `fd_slot()` 对 NULL 表做下标。C3 模拟器上就是：

```text
exec: process or thread table full
[bus] unmapped read @0x00000018
...（共 11 行，步长 sizeof(file_t)=24）
```

（上面的地址/步长是用临时 instrumentation 打上 pc 定位到 `fd_close_in` 才确认的，
instrumentation 未入库。）

修法两条，都是同一条规则：`fd_slot()` 对没有进程表的线程返回 NULL（= 没有这个
描述符），`proc_retire()` 只为主线程关描述符。`emutest` 现在把
`[bus] unmapped` 当失败，回归会被盯住。
