## 做了什么

- **两头分配**：栈区锚定在 `PLAT_APP_MAX`，按 4 KiB 单元从顶部向下编号；
  初始 16 KiB，分配不下时按 16 KiB 步进扩展，最下面一整步空闲时缩回。
  扩展前扫描窗口表，要求新下沿 ≥ 最高数据窗末尾 + 4 KiB；缩小后地址空间
  重新可以被数据窗使用。buddy 仍是 4/8/16 KiB 的 2 的幂对齐块。
- **数据窗**：`exec()` 只申请 `max(span, raw_size) + heap`，上界是
  `stack_area_low - 4 KiB`；`heap_end = base + win`，两个区之间的 4 KiB
  空洞就是 guard。不再有 `HEAP_GUARD` 的 4 KiB 预留在窗口内。
- **主线程栈**：`proc_create_claim()` 在窗口记录后从栈区取 `TOS_STACK`，
  `p->stack_top/size` 指向栈区块；`proc_retire_locked()` 对主线程和 worker
  一视同仁地归还。`build_initial_stack`、poison、高水位扫描都不变。
- **保护**：`apply_protection()` 在栈区块属于线程时用**当前线程**的
  `stack_top/size`（无栈区的板子仍用组长的窗口顶栈），段按地址排序；
  protection 缓存键也改成本次真正编程的栈，否则 worker→主线程回切会
  以为“没变化”，把兄弟的 PMP 留在 CPU 上（本轮抓到的实际 bug）。
- **join 的退出码指针**：可能落在 joiner 自己的栈区块上，`group_user_ok()`
  现在也接受该线程的栈范围。
- **canary/增长**：栈区块没有 canary（块下面是 buddy，不属于本线程），
  `process_stack_guard()` 直接放行，`process_stack_grow()` 直接拒绝。
- **user/kthread.c**：栈区请求单独向上取 2 的幂。原型 1 把 4096 先加成
  4112，内核按“非 2 的幂”回 `-2`，于是所有 kthread 都回退到堆——原型 1 的
  kthreadtest 没有覆盖栈区（已在其卡片中更正）。
- **x86**：内核镜像 102848 B，超过 200 扇区（102400 B）；`KERNEL_SECTORS`
  改为 202，littlefs LBA 从 201 移到 203（`stage1.S`、`build.go`、
  `board/pc/layout.c` 同步，构建期交叉校验通过）。

## 验证了什么 / 没验证什么

- **验证了**：C3 上主线程栈确实在栈区（`ps` 的 `wink` 不含栈，`stk/sz`
  是独立块）；两个 worker 的栈窗互不重叠；`deep` 的下溢立即 fault；
  `thread_create` 的 4K/8K/16K 块、join/exit 回收和重复 churn 正常；
  无栈区板子（ARM/rv32/rv32smp QEMU）行为不回退；x86 在新 LBA 上能启动。
- **没验证**：`free` 的 tasks 行仍按整个用户区统计，栈区没有单独数字；
  1000 次 4K/16K 混合长跑没做（200 次 churn 和 threadbench 重复已过）；
  RP2040 / Pico 2 的 T3/T4 未跑（未接板）；ARM 的 MPU 栈区、x86/RP2040
  的栈区布局都没有启用。
