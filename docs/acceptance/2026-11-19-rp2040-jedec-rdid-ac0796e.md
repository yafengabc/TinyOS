What changed and how it was proved
----------------------------------
1. RP2040 RDID.  The RP2040 has no QMI; the flash hangs off a PL022 SSI.
   rp_flash_rdid() (section .data.flash_ram, i.e. SRAM) copies the boot2
   image out of XIP, calls rom_connect/rom_exit_xip, then drives the SSI by
   hand.  After exit_xip the ROM has already left the SSI in the right mode
   (CTRLR0 = 7<<16: 8-bit frames, TMOD 00, Motorola mode 0, SSIENR = 1), so
   the probe touches only RXFLR/SR/DR0 and forces the chip select through
   the QSPI pad override on IO_QSPI io[1] - which is what the SDK's
   flash_do_cmd_cs() does, because the override outranks SSI_SER.  Five
   byte exchanges, then flush and the boot2 copy re-enters XIP.  The ID is
   read from rx[1..3] and stored through the out pointer; the capacity
   decode uses decimal 20..24 bounds.

2. plat_flash_detected_bytes() caches.  The first caller is ramdisk_init(),
   which kmain() runs before cpu_init() and before interrupts are enabled -
   so the probe runs single-core with nothing to park, and the SMP image
   needs no parking handshake at boot.  Later callers (/proc/flash, df) read
   the cache.

3. plat_block_count() follows plat_lfs_blocks() now (was PLAT_LFS_BLOCKS * 8),
   so the measured size actually reaches the mounted filesystem.

4. Why min() was wrong.  min(detected, configured) protects the case where
   board.conf overstates the chip, but it also makes a deliberately
   conservative board.conf a hard ceiling.  Reading the part is strictly
   better information: 4 MiB measured on a 1 MiB configuration means the
   chip really is 4 MiB.  The mount guard in ramdisk_init still compares a
   superblock against this value, so an oversized image is refused.

5. Disassembly check (rpi-pico): rp_flash_rdid sits at 0x20000021 in the SRAM
   section; the RXFLR loads feed `cmp #0`, DR0 is reached as base+0x3c from
   the RXFLR literal, the three-byte combine and the store through `out` are
   present, and every `blx` in the function goes to a ROM pointer or the
   boot2 copy - nothing executes from flash while XIP is off.  No decode
   folding: the capacity bounds are decimal 20..24.

What went wrong between ac0796e and 58a45e8
-------------------------------------------
The first probe reported detected 0 on every boot and cost four flash cycles.
Each cause was only visible in /proc/flash's probe_dbg dump, so that dump is
now part of the port (a weak plat_flash_probe_debug() hook, printed only when
detection fails):

  a) SER does not select the part.  After exit_xip the ROM pins the SS pad
     with the QSPI pad override, and the override wins over SSI_SER, so CS
     stayed high while the SSI happily clocked five frames.
  b) OUTOVER is 0 normal / 1 inverted / 2 force low / 3 force high.  Written
     as 0/1 the probe reported five bytes read and a junk ID (0x00000000
     after the sanity check), because the part was still never selected.
  c) SR's not-empty flag is ambiguous across documents (bit 2 vs bit 3).
     Trusting the wrong one produced a probe that always timed out, and then
     an unbounded drain loop that hung the boot inside ramdisk_init() - the
     board printed up to "[p] timer init" and stopped.  RXFLR (a byte count)
     replaced it and every loop is now bounded.
  d) rx[0] is not the opcode echo: this part starts driving MISO only after
     the opcode is clocked in, so the first byte is 0xff and the ID lands in
     rx[1..3].  A check for rx[0] == 0x9f rejected a correct measurement.
     The real validation is the caller's capacity-code range check.
